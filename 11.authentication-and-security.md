# Authentication and Security

## Current authentication decision

The site is public, static, and read-only. It has no user accounts, admin area, sessions, database, form submission, or authenticated API. Authentication would add complexity without solving a current requirement.

## Current security controls

- Removed the old Web3Forms contact form and its access key from the active page.
- Contact uses direct public profile links instead of accepting visitor input.
- External links opened in a new tab use `noopener noreferrer`.
- No runtime dependencies, cookies, tracking scripts, or secret-bearing server calls.
- Project status and skill claims are presented conservatively.

## Required owner action

The prior `index.html` contained a Web3Forms access key. It was present in a public browser file and must be treated as exposed, even though the new page no longer includes it. Revoke or rotate that key in the provider dashboard, inspect provider logs if available, and check Git history before making the repository public. Removing a secret in a later commit does not remove it from earlier commits.

## Future security requirements

If a contact endpoint, content editor, or authentication is later added:

- Keep secrets only in server-side secret storage; never in HTML, CSS, JavaScript, or committed configuration.
- Use HTTPS, secure session cookies, CSRF protections where cookie authentication applies, and strong rate limits.
- Apply least privilege and validate/authorize every server-side action.
- Add abuse prevention, input bounds, safe output encoding, retention/privacy disclosures, and operational logging without sensitive payloads.
- Threat-model the feature, update the architecture/API docs, and test negative paths before release.
- Do not add login solely to make the portfolio seem more complex.

## Security review checklist

- Search shipped files and current Git changes for tokens, passwords, private keys, and personal data.
- Confirm no unneeded form or external script is loading.
- Confirm external-link target behavior and HTTPS URLs.
- Verify hosting uses HTTPS and security headers where the platform supports them.
