# Database and Data Model

## Current decision: no database

The portfolio is a static resume site. Its content changes with source edits and is versioned by Git. It has no login, form submission, saved visitor preferences, content administration, or query needs that justify storing data in a database.

The profile, skills, and project roadmap live directly in `index.html`. This keeps the deployment simple, avoids infrastructure cost and maintenance, and reduces privacy and security exposure.

## Data currently displayed

| Content | Source | Persistence |
|---|---|---|
| Name and professional copy | HTML | Git |
| Skill categories and tags | HTML | Git |
| Planned project descriptions | HTML | Git |
| Public profile URLs | HTML | Git |
| Current copyright year | Browser runtime | Not persisted |

No visitor data is collected by the current implementation.

## Future decision criteria

Consider persistence only if the portfolio gains a concrete requirement such as a private content editor, frequently updated project data, or a backend contact workflow. Prefer static JSON or a build-time content source for public read-only projects. A database introduces deployment, access-control, backup, migration, and privacy obligations.

## Possible future entities (not implemented)

If project content moves to an API, a minimal model could include:

```text
Project
  id: stable slug
  title: required text
  summary: required text
  status: planned | in-progress | complete
  technologies: list of labels
  repository_url: optional validated HTTPS URL
  demo_url: optional validated HTTPS URL
  case_study: optional markdown/text
  published_at: optional timestamp
```

Avoid storing visitor data, credentials, resume-private details, or contact-message contents unless an explicit product requirement and retention policy exist.
